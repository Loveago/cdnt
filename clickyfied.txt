Base Setup

Common Request Headers
Name	Data Type	Required	Description
Authorization	string	Yes	Bearer token for the API secret. Use the format Authorization: Bearer <api_secret>.
X-Client-Id	string	Yes	Client identifier supplied with every request.
Idempotency-Key	string	Yes, for POST /orders	Unique key used to prevent duplicate order submissions.
Order Submission Body
Name	Data Type	Required	Description
externalReference	string	Yes	Partner reference for the order, such as an invoice number.
callbackUrl	string	No	Optional webhook URL used for order and not-received callbacks.
callbackSigningSecret	string	No	Optional shared secret used to sign callback payloads.
entries	array	Yes	List of order entries. Each entry includes a phone number and allocation value.
idempotencyKey	string	No	Optional fallback value for the same purpose as the Idempotency-Key header.
Path Parameters
Name	Data Type	Required	Description
orderId	string	Yes	Order identifier used in paths such as /orders/{orderId} and /orders/{orderId}/not-received.
Query Parameters
Name	Data Type	Required	Description
limit	integer	No	Page size for listing orders. Defaults to 20 and is capped at 100.
offset	integer	No	Pagination offset for listing orders. Defaults to 0.
status	string	No	Filters listed orders by status. Supported values: pending, processing, processed.
Response Types
This section describes the structure of all response objects returned by the API. Use these schemas as a reference when processing API responses.

Order Object
{
  orderId: string;                    // Unique identifier for the order
  externalReference: string;          // Partner reference passed during order creation
  status: "pending" | "processing" | "processed";  // Current order status
  createdAt: string;                  // ISO 8601 timestamp when order was created
  updatedAt: string;                  // ISO 8601 timestamp of last update
  entries: OrderEntry[];              // Array of order entries (see OrderEntry below)
  totalCount: number;                 // Total number of unique phone entries
  processedCount: number;             // Number of entries that have been processed
  clientId: string;                   // Client ID associated with this order
  callbackUrl?: string;               // Optional webhook URL for callbacks
}
OrderEntry Object
{
  id: string;                         // Unique identifier for this entry
  number: string;                     // Phone number (with or without country code)
  allocationGB: number;               // Data allocation in gigabytes
  status: "pending" | "processing" | "processed";  // Current status of this entry
  createdAt: string;                  // ISO 8601 timestamp when entry was created
  updatedAt: string;                  // ISO 8601 timestamp of last update
}
NotReceivedReport Object
{
  reportId: number;                   // Unique identifier for this report
  orderId: string;                    // Order ID this report relates to
  status: "pending_resolution" | "confirmed_sent" | "resolved" | "cancelled";
  reportDate: string;                 // ISO 8601 timestamp when report was submitted
  resolutionDate?: string;            // ISO 8601 timestamp when report was resolved
  adminNotes: string;                 // Notes from the admin investigating the issue
  evidenceUrl?: string;               // URL to evidence (screenshot, receipt, etc.)
  evidenceType?: string;              // Type of evidence: "screenshot", "receipt", "log", etc.
  channel?: string;                   // How the issue was resolved: "groupshare", "manual", "other"
}
ApiResponse Wrapper
Successful API responses are wrapped in a standard response object:

{
  success: boolean;                   // true for successful requests
  message?: string;                   // Optional success message
  // ... additional fields based on the endpoint
}
Error responses follow this structure:

{
  success: false;
  error: string;                      // Descriptive error message
  code?: string;                      // Optional error code for programmatic handling
  details?: object;                   // Optional additional error details
}
Callback Payload Object
All callbacks include this base structure:

{
  event: string;                      // Event type: "order.accepted", "order.status.changed", etc.
  orderId: string;                    // Order ID related to this event
  clientId: string;                   // Client ID that created the order
  timestamp: number;                  // Unix timestamp (milliseconds)
  // ... event-specific fields
}
Error Handling Guide
HTTP Status Codes Reference
All API responses use standard HTTP status codes. Below is a comprehensive reference:

Status Code	Meaning	Description	Retry Strategy
200	OK	Request succeeded	N/A
201	Created	Resource created successfully (POST requests)	N/A
400	Bad Request	Invalid request parameters, validation failed	Don't retry
401	Unauthorized	Missing or invalid authentication credentials	Don't retry (fix credentials)
403	Forbidden	Authenticated but not authorized for resource	Don't retry
404	Not Found	Resource (order, client) doesn't exist	Don't retry
409	Conflict	Resource already exists (e.g., duplicate order)	Don't retry
422	Unprocessable Entity	Business logic validation failed (e.g., user halted)	Don't retry immediately
429	Too Many Requests	Rate limit exceeded; see Retry-After header	Retry after Retry-After seconds
500	Internal Server Error	Server error; something went wrong	Retry with exponential backoff
503	Service Unavailable	Server is temporarily unavailable	Retry with exponential backoff
Error Response Structure
When an error occurs, the API returns a JSON response with this structure:

Base Error Structure:

{
  "success": false,
  "error": "Human-readable error message",
  "code": "ERROR_CODE",
  "details": {
    "field": "additional_context"
  }
}
Common Error Scenarios
1. Validation Error (400 Bad Request)
Cause: Invalid phone number format, missing required fields, or invalid data

Example Response:

{
  "success": false,
  "error": "Validation failed",
  "code": "VALIDATION_ERROR",
  "details": {
    "entries": [
      {
        "index": 0,
        "number": "+123invalid",
        "reason": "Invalid phone number format"
      }
    ]
  }
}
How to Handle:

Check the details object for field-specific errors
Validate input data before sending (phone format, required fields)
Display meaningful error messages to users
2. Authentication Failed (401 Unauthorized)
Cause: Missing Authorization header, invalid API secret, or missing X-Client-Id

Example Response:

{
  "success": false,
  "error": "Unauthorized: Missing or invalid API credentials",
  "code": "INVALID_CREDENTIALS"
}
How to Handle:

Verify API secret and client ID are correct
Ensure Authorization: Bearer <secret> header is present
Ensure X-Client-Id header is included in all requests
Check that credentials have not been revoked or expired
3. Order Not Found (404 Not Found)
Cause: Trying to access an order with an invalid or non-existent orderId

Example Response:

{
  "success": false,
  "error": "Order not found",
  "code": "ORDER_NOT_FOUND",
  "details": {
    "orderId": "invalid-order-123"
  }
}
How to Handle:

Verify the orderId is correct
Check that the order belongs to your API client
Ensure you're using the correct server (sandbox vs production)
4. Duplicate Order (409 Conflict)
Cause: Attempting to create an order with an externalReference that already exists

Example Response:

{
  "success": false,
  "error": "Order with this external reference already exists",
  "code": "ORDER_ALREADY_EXISTS",
  "details": {
    "externalReference": "invoice-20260903-001",
    "existingOrderId": "ext-seraph-001-67890"
  }
}
How to Handle:

Use the existing order ID returned in details, or
Generate a unique externalReference and retry, or
Use idempotent retry with the same Idempotency-Key (see Action 2)
5. Rate Limit Exceeded (429 Too Many Requests)
Cause: API or polling rate limits exceeded

Example Response:

{
  "success": false,
  "error": "Rate limit exceeded. Please try again later.",
  "code": "RATE_LIMIT_EXCEEDED",
  "details": {
    "retryAfter": 30,
    "limit": "100 requests per minute"
  }
}
Response Headers:

Retry-After: 30 - Wait this many seconds before retrying
How to Handle:

Read the Retry-After response header
Wait the specified number of seconds before retrying
Implement exponential backoff for subsequent retries
For polling, respect the 30-second minimum interval per order
6. Business Logic Error (422 Unprocessable Entity)
Cause: User account is halted, insufficient permissions, or other business constraints

Example Response:

{
  "success": false,
  "error": "User account is halted and cannot process orders",
  "code": "USER_ACCOUNT_HALTED",
  "details": {
    "reason": "Payment overdue",
    "haltedAt": "2026-09-01T12:00:00.000Z"
  }
}
How to Handle:

This is a business rule violation; investigate the specific code
Contact support if the issue persists
Don't immediately retry; check account status first
7. Server Error (500 Internal Server Error)
Cause: Unexpected server error

Example Response:

{
  "success": false,
  "error": "Internal server error. Please try again later.",
  "code": "INTERNAL_SERVER_ERROR",
  "details": {
    "requestId": "req-abc123xyz"
  }
}
How to Handle:

Retry with exponential backoff (1s, 2s, 4s, 8s, etc.)
Save the requestId for debugging
If repeated, contact support with the request ID
Error Handling Best Practices
1. Always check the success flag:

const response = await fetch(url, options);
const data = await response.json();

if (!data.success) {
  // Handle error
  console.error(`Error [${data.code}]: ${data.error}`);
  if (data.details) {
    console.error('Details:', JSON.stringify(data.details, null, 2));
  }
  // Take appropriate action based on error code
}
2. Implement proper retry logic:

async function apiCallWithRetry(url, options, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    try {
      const response = await fetch(url, options);
      const data = await response.json();
      
      if (data.success) {
        return data;
      }
      
      // Don't retry client errors (4xx)
      if (response.status >= 400 && response.status < 500) {
        throw new Error(`Client error: ${data.error}`);
      }
      
      // Retry server errors (5xx)
      if (response.status >= 500) {
        const waitTime = Math.pow(2, attempt) * 1000; // Exponential backoff
        await new Promise(resolve => setTimeout(resolve, waitTime));
        continue;
      }
      
      throw new Error(data.error);
    } catch (error) {
      if (attempt === maxRetries - 1) throw error;
    }
  }
}
3. Handle rate limiting with Retry-After:

if (response.status === 429) {
  const retryAfter = parseInt(response.headers.get('Retry-After') || '60');
  console.log(`Rate limited. Retrying after ${retryAfter}s`);
  await new Promise(resolve => setTimeout(resolve, retryAfter * 1000));
  // Retry the request
}
4. Log errors for debugging:

if (!data.success) {
  console.error({
    timestamp: new Date().toISOString(),
    endpoint: url,
    statusCode: response.status,
    errorCode: data.code,
    errorMessage: data.error,
    details: data.details,
    requestId: data.details?.requestId
  });
}

Callback Signature Verification
If you configured a callbackSigningSecret when creating your API client, each callback will include an X-External-Signature header.

To verify the signature:

Extract X-External-Signature from the callback headers
Compute HMAC-SHA256 of the raw request body using your callbackSigningSecret as the key
Compare the computed hash (as hex string) with the header value
Example verification in Node.js:

const crypto = require('crypto');

function verifyCallbackSignature(rawBody, headerSignature, secret) {
  const computed = crypto
    .createHmac('sha256', secret)
    .update(rawBody)
    .digest('hex');
  
  return computed === headerSignature;
}
Example verification in Python:

import hmac
import hashlib

def verify_callback_signature(raw_body, header_signature, secret):
    computed = hmac.new(
        secret.encode(),
        raw_body.encode() if isinstance(raw_body, str) else raw_body,
        hashlib.sha256
    ).hexdigest()
    
    return computed == header_signature
Callback Timeout & Retry
Callbacks are sent with a 10-second timeout
If your endpoint responds with a status other than 200-299, the callback is automatically retried up to 3 times
Retry delays: 30 seconds, 5 minutes, 1 hour
If all retries fail, the callback is logged but not attempted again
Best Practices
Respond quickly - Acknowledge the callback within a few seconds
Verify signatures - Always verify the X-External-Signature if a secret is configured
Idempotent processing - Process callbacks idempotently in case duplicates are received
Log events - Store callback records for audit and debugging purposes
Monitor 429s - If you receive many callbacks, you may be hitting rate limits; consider polling instead
